## Product and UI

- Port the existing `scripts/ui-design-demo/index.html` into React + Vite. Keep its restrained, modern SaaS style, English-first copy, pink/blue and pink/purple palette, and Pulse / Wave / Loop theme icons. Treat the existing design as the visual and interaction reference, while replacing hard-coded sample behavior with real state and API calls.
- On desktop, Notes and Transcript occupy equal-width columns. Keep Sources within the transcript-side view, plus the floating Ask Playback / explanation popup. On narrow screens, preserve the mobile tab layout; mobile is UI-only for this phase.
- Notes are editable Markdown with preview, links, lists, and **flowcharts/graphs embedded in the Markdown**. Use a maintained renderer with safe sanitization and a diagram format such as Mermaid; store the source Markdown so it stays editable. A graph must be a real rendered diagram, not merely a paragraph describing one.
- Transcript entries show a **start–end time range**, speaker/source, immutable ASR original, optional translation/revision, and uncertainty. A click should seek the corresponding locally available audio range. Keep model suggestions visibly separate from ASR original.
- Keep Key Ideas visually concise and free of mandatory reference markers. Explanations and answers that rely on lecture material or web search should provide optional, clickable evidence and label model inference clearly. Do not put development terms such as “demo” or “mock” in the product UI.

## Implementation scope

1. Start with a short feasibility audit of the existing spikes. Confirm SDK/API versions and current model IDs against official docs. Separate verified, unverified, and environment-blocked capabilities. Use synthetic text/audio for initial external probes. Programs may load `.env` into their process environment; do not print keys or file contents.
2. Build a .NET 10 C# local API as one readable application. Use Microsoft Agent Framework for the rolling-note and question-answering agent flow; do not use Semantic Kernel. Use `gemini-3.8-flash` for agent work and `gemini-3.5-flash-lite` for bounded simple tasks such as explanation, translation, and a small Google Search grounding test. The AI Studio path reads `GOOGLE_AI_STUDIO_API_KEY` from the process environment. Treat Vertex AI as a separate deployment/authentication configuration; do not label an AI Studio request as Vertex AI.
3. Implement a small Jev adapter for **candidate** term ranking and “suggest more explanation?” classification. Discover the available model with `GET /v1/models`, then call `POST /v1/systemone` using the current official TypeSafe schema and `JEV_API_KEY` from the process environment. Compare it with a simple rule and a Gemini classifier on a small labeled synthetic set; record latency, returned confidence, cost/usage where available, and failure behavior. Jev does not write explanation prose or infer an individual student's understanding. If its credential/access is unavailable, expose this capability as unavailable and keep the rest working; do not silently substitute a successful mock.
4. For web-backed explanation, call the official Gemini Google Search grounding API where supported, preserve its returned citation annotations, and display links only when evidence is present. The .NET Agent Framework Gemini C# integration currently lists provider-hosted Web Search as unsupported, so isolate the grounded call at the application boundary and verify current support before choosing its implementation. Keep lecture-source retrieval and public web evidence distinguishable.
5. Provide a real SenseVoice ASR adapter for `POST https://dev-aks.setsailapi.com/stt/infer/upload` with multipart field `file`. Make the fixed endpoint configurable only through an explicit allowlist. Use bounded request/response sizes, timeouts, no redirects, visible errors, and idempotent retry keyed by session/source/sequence/hash. A local synthetic fixture may exercise the path before any permitted real recording is sent.
6. Build a native-owned local audio capture and durable chunk queue, with Electron + TypeScript as the first desktop candidate. Browser refresh, UI navigation, API outage, and app reconnect must not lose chunks. Capture whole-system playback audio and microphone as separate sources with timestamps; verify Windows first in the available environment. Document and then test macOS separately when hardware/permissions are available; do not claim cross-platform capture without a real check. Detect silent streams and permission failures. Do not mix sources until alignment is proven. Provide pause/resume, recovery after restart, pending-upload status, playback of retained chunks, and a safe local stop.
7. Use local MongoDB for session, transcript, note-version, source, and citation metadata, following `docs/scope-decision.zh-HK.md`. The existing PostgreSQL module remains a study spike. Store raw ASR, translation, note revisions, and links to audio time ranges separately. Keep audio chunks durable locally during the prototype; Cloud Storage/Cloud Run/Atlas deployment is outside this task. Keep classroom material and conversation scoped per session; private questions stay private.
8. Connect frontend and backend end to end: create a session, attach material, start/stop capture, see live transcript and rolling note updates, edit Markdown, render a flowchart, open a term explanation, ask a question, inspect evidence, seek audio, and recover after restart. Show honest pending/error/uncertain states, with no silent success fallback.
